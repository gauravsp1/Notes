Redux

Redux is a popular state management library for JavaScript applications, particularly those built with React. 
It helps manage the state of an application in a predictable way, enabling easier debugging, testing, and scaling of applications.
Manage global state in one place
Make state predictable and debuggable
Share state across deeply nested components


Key Concepts of Redux

Single Source of Truth:
The entire state of the application is stored in a single JavaScript object called the store. This makes the state management more predictable and easier to debug.

State is Read-Only:
The only way to change the state is to emit an action, an object describing what happened. This ensures that the state is not modified directly, 
which helps in tracking changes and maintaining predictability.

Changes are Made with Pure Functions:
To specify how the state tree is transformed by actions, you write pure functions called reducers.
Reducers take the current state and an action as arguments and return a new state.

Core Components of Redux

Store:
The store holds the whole state tree of the application. There is only one store in a Redux application.
import { createStore } from 'redux';
import rootReducer from './reducers';

const store = createStore(rootReducer);

Actions:
Actions are payloads of information that send data from the application to the store. They are the only source of information for the store.
const increment = () => {
  return {
    type: 'INCREMENT'
  };
};

Reducers:
Reducers specify how the application's state changes in response to actions sent to the store. They are pure functions.
const counter = (state = 0, action) => {
  switch (action.type) {
    case 'INCREMENT':
      return state + 1;
    case 'DECREMENT':
      return state - 1;
    default:
      return state;
  }
};

Dispatch:
dispatch is the method used to send actions to the store.
store.dispatch(increment());

Selectors:
Selectors are functions that extract and transform pieces of the state. They help in decoupling the state shape from the component logic.
const getCounterValue = (state) => state.counter;

Connecting Redux to React
To connect Redux with React, you typically use the react-redux library, which provides two main features: Provider and connect.

Middleware in Redux
Middleware is a way to extend Redux with custom functionality. Middleware allows you to intercept actions 
before they reach the reducer and perform additional logic such as logging, asynchronous API calls, etc.

Middleware ******
Redux middleware provides a third-party extension point between dispatching an action, and the moment it reaches the reducer. 
People use Redux middleware for logging, crash reporting, talking to an asynchronous API, routing, and more.

Middleware allows for side effects to be run without blocking state updates. 
We can run side effects (like API requests) in response to a specific action,

Redux Thunk middleware allows you to write action creators that return a function instead of an action. 
The thunk can be used to delay the dispatch of an action, or to dispatch only if a certain condition is met. 
Used to make api calls

Redux Thunk is a middleware that lets you call action creators that return a function instead of an action object. 
That function receives the store’s dispatch method, which is then used to dispatch regular synchronous actions inside the function’s body 
once the asynchronous operations have been completed.

Once Redux Thunk has been installed and included in your project with applyMiddleware(thunk), you can start dispatching actions asynchronously.

Redux Thunk is a middleware that allows you to call the action creators that return a function(thunk) 
which takes the store's dispatch method as the argument and which is afterwards used to dispatch the synchronous action after the API 
or side effects has been finished.

Why Use redux-thunk?
By default, Redux actions must be plain objects. This limitation means that asynchronous logic, such as API calls or complex computations, 
cannot be handled directly within action creators. redux-thunk addresses this limitation by allowing action creators to return a function instead of an action. 
This function receives the store's dispatch method as an argument, allowing you to dispatch actions asynchronously.


thunk vs saga
Thunk is the default middleware in Redux that lets you write action creators as functions instead of plain objects.
Just uses plain async/await
Easy to integrate and debug
Good for small/medium apps

Saga uses generator functions (function*) and effects like yield call, yield put, etc. to orchestrate complex side effects in a predictable way.
Saga runs separately from components
Supports cancellation, race conditions, retries, etc.
Ideal for real-world apps with complex logic

| Style       | Thunk                | Saga                        |
| ----------- | -------------------- | --------------------------- |
| Imperative  | “Do this, then that” | “What needs to be done”     |
| Declarative | ❌ No                 | ✅ Yes (via `yield` effects) |


Use Redux Thunk When...
✅ You are building a small or medium-scale app
✅ You only need to perform simple async operations (like API calls)
✅ You or your team are new to Redux or async middleware
✅ You prefer using familiar JavaScript (async/await) without learning advanced concepts
✅ You want minimal boilerplate and faster setup

📦 Typical Thunk Use Cases
Fetching a list of products or users
Submitting a form and showing a success message
Dispatching actions based on one async call
Fetch-on-mount use cases (useEffect + dispatch)


Use Redux Saga When...
✅ Your app has complex async workflows
✅ You need fine-grained control over time (e.g., delays, throttling, race conditions)
✅ You want testable side-effect code with clean unit tests
✅ You deal with cancellation, retries, chained calls, or background tasks
✅ You're working on a large-scale production app or a team-based codebase where scalability matters

📦 Typical Saga Use Cases
Debounce user input (e.g., search typing)
Cancel API call if a new one starts
Retry failed requests with exponential backoff
Complex sequences (e.g., login → fetch profile → route → analytics)
Long-running processes like file uploads or WebSocket management

| Middleware | Analogy                                                                            |
| ---------- | ---------------------------------------------------------------------------------- |
| **Thunk**  | A direct phone call: simple, quick, but manual                                     |
| **Saga**   | A well-trained assistant: can do complex sequences, retry, cancel, and report back |

| Project Complexity                        | Recommended Middleware |
| ----------------------------------------- | ---------------------- |
| Basic data fetching                       | **Thunk**              |
| Async + retry/cancel/delay                | **Saga**               |
| Very large team with testing requirements | **Saga**               |
| You hate generator functions 😅           | **Thunk**              |


In Saga
| Effect            | Purpose                          |
| ----------------- | -------------------------------- |
| `takeLatest`      | Auto-cancel previous, run latest |
| `cancel` + `fork` | Manual cancel control            |
| `retry`           | Retry with delay and attempts    |
| `debounce`        | Delay execution after inactivity |
| `race`            | Compete between two async ops    |


Redux vs useContext******

| Feature     | **Context API**                       | **Redux / Redux Toolkit**                       |
| ----------- | ------------------------------------- | ----------------------------------------------- |
| Scope       | Localized/global **sharing of state** | Full-blown **global state management**          |
| Use Case    | Prop drilling prevention              | Complex app state: CRUD, caching, normalization |
| Tooling     | Built into React                      | External library                                |
| DevTools    | Minimal / none                        | Excellent Redux DevTools support                |
| Boilerplate | Low (with `useContext`)               | Low (with Redux Toolkit) but still structured   |
| Middleware  | No support                            | First-class (e.g., redux-thunk, redux-saga)     |
| Async       | Manual via `useEffect`                | Built-in support via `createAsyncThunk`         |

Drawbacks of Context API ***

Re-renders entire subtree
Any change in context triggers a re-render of all consuming components under the provider—even if they don’t use the updated value.
This can seriously hurt performance in large UIs.

Not designed for frequent updates
It works best for static or rarely-changing values (e.g., theme, locale, auth).
Avoid for dynamic, fast-updating state (e.g., input forms, counters, timers).

No dev tooling
You won’t get time travel, logging, or visual tracking like Redux DevTools.

Drawbacks of Redux ***

More abstraction & learning curve
Even with Redux Toolkit, beginners might find createSlice, thunks, and middleware intimidating.
Needs setup (store, slices, provider).

Verbosity (without Toolkit)
Legacy Redux is boilerplate-heavy. Toolkit improves this a lot but adds magic (which some teams dislike).

Overkill for simple app
Using Redux just for two counters and one user list? Probably not worth it.

What Does "Re-renders Entire Subtree" Mean In Context-API ****
When you update the value passed to a React Context <Provider>, React will re-render every component that consumes that context and
is located under that Provider in the component tree — even if the new value doesn't affect that specific component.
If a context value changes, React invalidates and re-renders everything that reads from that context, regardless of whether or not it really needed the update.

This behavior is fine for small apps. But in large-scale apps, where components may be complex and render-heavy:
It wastes render cycles.
It can lead to janky UI and performance bottlenecks.
It becomes hard to reason about what’s actually being re-rendered.


When to Use Redux:
App has complex shared state, like: Nested updates , Multiple sources of truth (auth, cart, notifications), Normalized or paginated data
You need global async logic (e.g., API handling, loading states).
You want time travel, logging, and great dev experience.

Multiple teams work on the same app.
When to Use useContext:
State is static or rarely changes (e.g., theme, locale, user auth).
You just need one or two shared values.
You want zero dependencies.
Performance is not a concern.


Different State management methods *****************

1. React's Built-in State Management:
useState Hook:
Purpose: Manages local component state within function components.
Best for: Small, local state management.
Pros: Simple, no setup, built-in to React.
Cons: Limited to managing state within a single component or tightly coupled components.

useReducer Hook:
Purpose: More suited for complex state logic that involves multiple sub-values or state transitions.
Best for: Complex state logic within a single component or a small set of components.
Pros: Reducer pattern is easy to manage and test.
Cons: Not as scalable for global state as Redux or Context.

useContext Hook:
Purpose: Provides a way to pass data (global-like state) to deeply nested components without prop drilling.
Best for: Sharing data globally or across multiple components, like theme settings or user authentication.
Pros: Simple and lightweight for small-to-medium apps.
Cons: Can lead to performance issues if not optimized (e.g., unnecessary re-renders).


2. Third-Party State Management Libraries:
Redux:
Purpose: Manages the global state of an entire application with a central store. Follows a strict pattern of state management with actions and reducers.
Best for: Large and complex applications where many components need to share and update global state.
Pros: Predictable state, time-travel debugging, dev tools, async logic with middlewares like redux-thunk or redux-saga.
Cons: Boilerplate-heavy, can be overkill for simple applications.

Redux Toolkit:
Purpose: A set of tools and abstractions built on top of Redux to simplify its setup and reduce boilerplate.
Best for: Developers who want to use Redux but with less boilerplate and better default patterns.
Pros: Simplifies Redux with slices, built-in createAsyncThunk for async operations, and built-in immutability.
Cons: Same learning curve as Redux but more streamlined.

MobX:
Purpose: A library for state management that focuses on reactivity. State changes automatically re-render components.
Best for: Developers who prefer an object-oriented approach to state management or want a simpler, more reactive model.
Pros: Easy to learn, minimal boilerplate, supports observables for automatic reactivity.
Cons: Less popular than Redux, making it harder to find community support.


Local Component State: Use useState or useReducer when managing state within individual components.
Context API: Use useContext for smaller applications or for global state that isn't very complex.
Redux/Redux Toolkit: Best for large, complex apps with global state and a need for predictability.
MobX/Recoil: Alternatives to Redux for reactive and fine-grained control over state, with simpler setup and reactivity.
Apollo Client/React Query: Perfect for managing server-side state in GraphQL or REST-based applications.


why reducers are pure functions***********
Reducers are pure functions because they:
Always return the same output given the same input (deterministic).
Do not cause any side effects.
Do not mutate their input data (immutability).
Are easy to test due to their pure nature.

Redux persistence***
“Redux persistence means saving the Redux store to a persistent storage (like localStorage) so that state survives a browser refresh.

Redux by default only accepts plain object actions:
store.dispatch({ type: "INCREMENT" });

So if you want to do async operations (like fetching data), the problem is:
const fetchData = () => {
  const data = await fetch("https://api.com"); // async
  return { type: "SET_DATA", payload: data }; // ❌ cannot await here in plain action
};
Without middleware, Redux cannot pause the action until async is done.

Alternatives to Middleware
Handle Async in Components
useEffect(() => {
  async function fetchUsers() {
    const res = await fetch("/api/users");
    const data = await res.json();
    dispatch({ type: "SET_USERS", payload: data });
  }
  fetchUsers();
}, [dispatch]);

Reducers are pure and synchronous by design — that’s what makes Redux predictable.
Redux reducers are pure functions and cannot perform side effects such as API calls or async operations.So, middleware like Redux Thunk is needed
